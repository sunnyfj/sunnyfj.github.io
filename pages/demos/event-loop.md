# Event loop 事件循环

##  浏览器进程模型

### 何为进程
程序运行时需要有它的专属内存空间，用于存储变量、函数、对象等。 可以把这块内存空间简单理解为进程

每个程序至少有一个进程，进程之间是独立的。即使需要通信，也需要双方同意

### 何为线程

有了进程，就可以运行程序代码了

运行代码的“人”称之为线程

每个进程至少有一个线程，所以在进程启动时，会默认创建一个线程，这个线程被称为主线程，主线程负责执行进程中的代码。主线程结束了，进程也就结束了。

如果程序需要同时执行多块代码（多项任务），主线程就会启动更多的线程来执行代码 所以一个进程可以有多个线程

### 浏览器有哪些进程和线程

`浏览器是一个多进程多线程的应用程序`

浏览器内部工作极其复杂。（现在浏览器内部的复杂度已经接近操作系统）

为了避免相互影响，为了减少连环崩溃的几率，当启动浏览器后，它会自动启动多个进程。

浏览器进程、 GPU进程、 Network Service进程、 Storage Service进程、 V8进程、 每个标签页进程。

其中，最主要的进程有：
- 浏览器进程：主要负责界面展示、用户交互、子进程管理等。（顶部导航栏、地址栏、书签栏、刷新按钮、前进后退按钮等）。浏览器进程内部会启动多个线程处理不同的任务。
- 网络进程（Network Process）：负责加载网络资源， 网络进程内部会启动多个线程来处理不同的网络任务。
- `渲染进程（Renderer Process）`(事件循环发生在渲染主线程中)：
    渲染进程启动后，会开启一个`渲染主线程`，主线程负责执行 HTML、CSS、JavaScript 代码。
    默认情况下，浏览器会为每个标签页开启一个新的渲染进程，以保证每个标签页的渲染不相互影响。
    (将来规划中 可能会改变这一行为，从标签页进程 过渡到 站点进程（Site Process  相同的站点在一个进程中）。或者更复杂的场景)
- GPU进程：整个浏览器中唯一有权限直接调用操作系统GPU硬件加速接口的进程。它是一个全局单例（通常只有一个）。
    接收指令：接收来自所有渲染进程以及浏览器主进程提交的绘图数据（如图层、图块、UI指令）。
    调度与调用：将这些数据调度、转换为OpenGL或DirectX等图形API调用，驱动GPU进行最终的`像素填充和屏幕合成`。
    统一资源管理：统一管理显存、纹理等GPU资源，避免多个渲染进程争抢。

## 渲染主线程是如何工作的

渲染主线程是浏览器中最繁忙的线程，需要处理的任务包括但不限于：
- 解析HTML
- 解析CSS
- 计算样式（Style Calculation）
- 布局（Layout）
- 处理图层
- 每秒把页面画 60 次（60Hz）
- 执行全局 js 代码
- 执行事件处理函数（如点击、滚动等）
- 执行计时器回调函数
- ...

为什么渲染进程不适用多个线程来处理这些事情？

要处理这么多的任务，主线程遇到了一个前所未有的难题： 如何调度任务？

比如：
- 我正在执行一个 js 函数，执行到一半，用户点击了一个按钮，我该立即执行事件处理函数吗？
- 我正在执行一个 js 函数，执行到一半，定时器到时间了，我该立即执行定时器回调函数吗？
- 浏览器进程通知我“用户点击了按钮”，与此同时，某个定时器也到时间了，我该先执行哪个？
- ...

浏览器 渲染主线程想出了一个绝妙的主意来处理这个问题： 排队

渲染主线程 ----- 【任务1, 任务2, 任务3, ...】 执行完去消息队列取任务 依次

消息队列   ----- 【事件1, 事件2, 事件3, ...】 排队

其他线程 给到消息队列排队（chrome 源码中 message_loop > 消息循环  w3c 标准中叫 event loop）

1.最开始的时候，渲染主线程会进入一个无限循环（ 源码中 > for(;;)  与 while(true) 一样 ））
2.每一次循环检查消息队列中是否有任务，如果有，就取出第一个任务执行，执行完后进入下一次循环，如果没有，进入休眠
3.其他所有线程（包括其他进程的线程）可以随时向消息队列添加任务。新任务会追加到末尾。在添加新任务时，如果主线程是休眠状态，则会将其唤醒以继续循环拿取任务

这样一来，就可以让每个任务有条不紊的、持续的执行下去。

`整个过程，被称之为事件循环（Event Loop） 或者 消息循环（Message Loop）`

## 若干解释

### 何为异步？

代码的执行过程中，会遇到一些无法立即完成的任务，比如：
- 网络请求
- 定时器
- 事件监听
- ...

如果让渲染主线程等待这些任务的时机到达，就会导致主线程长期处于“阻塞”状态，从而导致浏览器“卡死”

`渲染主线程承担着极其重要的工作，无论如何都不能阻塞！`

因此，浏览器采用了异步的方式来解决这个问题

使用异步的方式，`渲染主线程永不阻塞`

#### 如何理解JS的异步？
JS是一门单线程的语言，这是因为它运行在浏览器的渲染主线程中，而渲染主线程只有一个。
而渲染主线程承担很多工作，渲染页面，执行JS 都在其中等。
如果同步的方式，就极有可能导致渲染主线程产生阻塞，从而导致消息队列中的其他任务无法得到执行。

这样一来，一方面会导致繁忙的主线程白白浪费时间，另一方面也会导致页面无法及时更新，给用户造成卡死现象。

所以浏览器采用异步的方式来避免。具体做法就是某些任务发生时，比如计时器。网络。事件监听。主线程将任务交给其他线程去处理，自身立即结束任务的执行，转而执行后续代码。当其他线程完成任务后，将任务回调函数添加到消息队列的末尾，等待渲染主线程调度执行。

在这种异步模式下，渲染主线程永不阻塞，从而最大限的保证了主线程的流畅运行。

#### js为何会阻碍渲染？

因为js和渲染都在渲染主线程中，而渲染主线程只有一个，所以js执行时，会阻塞渲染。

#### 任务有优先级吗？

任务没有优先级，在消息队列中，先进先出。

但`消息队列是有优先级的`

根据 W3C 最新的解释：
- 每个任务都有一个任务类型（Task Type），同一个类型的任务必须在一个队列，不同类型的任务可以分属不同的队列。在一次事件循环中 浏览器可以根据实际情况从不同的队列中取出任务执行。（这就造成了不同浏览器的实现有差异）
- 浏览器必须准备好一个微队列（Microtask Queue），微队列中的任务优先所有其它任务执行

** 随着浏览器的复杂急剧增加，W3C 不再使用宏队列的说法

在目前的 Chrome 的实现中，至少包含了以下队列：
- 延时队列： 用于存放计时器到达的回调任务，优先级 中
- 交互队列： 用于存放用户操作产生的事件处理任务， 优先级 高
- 微队列：用于存放需要最快执行的任务，优先级 最高
- ...

** 添加任务到微队列的主要方式是使用 Promise、MutationObserver 等 API

```js
// 示例：使用 Promise 添加任务到微队列
Promise.resolve().then(() => {
  console.log('微队列任务')
})
```

#### 阐述一下js的事件循环

事件循环又叫做消息循环，是浏览器渲染主线程的工作方式。
从chrome的源码中，它开启一个不会结束的for循环，每次循环从消息队列中取出第一个任务执行，而其它线程只需要在合适的时候将任务添加到消息队列的末尾。

过去把消息队列简单的分为宏队列和微队列，这种说法目前已经无法满足复杂的浏览器环境，取而代之的是一种更加灵活多变的队列处理机制。

根据 W3C 最新的解释，每个任务都有一个任务类型（Task Type），同类型的任务必须在同一个队列，不同类型的任务可以分属不同的队列。不同任务队列有不同的优先级，在一次事件循环中，由浏览器自行决定从哪个队列中取出任务执行。但浏览器必须有一个微队列，微队列中的任务一定具有最高的优先级，必须优先调度执行。

#### js 中的计时器能做到精准的时间吗？

不能。

因为：
1.计算机硬件没有原子钟，无法做到精准的时间
2.操作系统的计时函数本身就有少量偏差，由于JS的计时器最终调用的是操作系统的函数，所以也会有偏差
3.按照W3C的标准，浏览器实现计时器时，如果嵌套层级超过5层，则会带有4毫秒的最小时间偏差
4.受事件循环的影响，计时器的回调函数必须要等渲染主线程空闲时才会执行，所以也会有偏差
