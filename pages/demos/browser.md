## 浏览器是如何渲染页面的？ 从输入url到页面展现出来都有哪些步骤？

流程：
网络线程：通信 > 拿取html字符串 > 渲染任务 > 消息队列
渲染主线程：拿到渲染任务 > 启动渲染
-----

总结：
当浏览器的网线程收到 HTML 文档后，会产生一个渲染任务，并将其传递给渲染主线程的消息队列

在事件循环机制的作用下，渲染主线程取出消息队列中的渲染任务，开启渲染流程

-----

总结过程：
整个渲染流程分为多个阶段，分别是：HTML 解析、样式计算、布局、绘制、分块、光栅化、画、像素信息

每个阶段都有明确的输入输出，上一个阶段的输出，是下一个阶段的输入。

这样，整个渲染流程就形成了一套组织严密的生产流水线。

-----

渲染的第一步是 `解析 HTML`。

解析过程中遇到 CSS 解析 CSS, 遇到 JS 执行 JS, 为了提高解析效率，浏览器在开始解析前，会启动一个预解析的线程，率先下载HTML中的外部 CSS 文件和 JS 文件。

如果主线程解析到link位置，此时外部的css文件还没有下载解析好，主线程不会等待，继续解析后续的html。 这是因为下载和解析css的工作是在预解析线程中进行的，这就是css 不会阻塞html解析的根本原因。

如果主线程解析到script位置，会停止解析html，转而等待js文件下载完成。 并将全局代码解析执行完成后，才能继续解析html。 这是因为JS代码执行过程可能会修改当前的 DOM 树，所以dom 树的生成必须暂停， 这就是JS 会阻塞html解析的根本原因。

第一步完成后，会得到 DOM 树和 CSSOM 树，浏览器的默认样式会、内部样式、外部样式合并成一个 CSSOM 树。

第二步 `样式计算`

(css 属性值的计算过程 层叠 集成   视觉格式化模型 盒模型 包含块（相对位置相对的就是包含块）)

主线程会遍历得到的 DOM 树， 依次为树中的每个节点计算出它最终的样式，称之为 computed style。

在这一过程中，很多预设值会变成绝对值， 比如red > rgb(255, 0, 0); 相对单位会变成绝对单位， 比如em > px;

这一步完成后，会得到一棵带有样式的 DOM 树

第三步 `布局` layout

（::before ::after 伪元素 会参与布局, 行内元素和块级元素只是html的  行盒 块盒是由css决定的，目前的html相当于只提供语义化 ， 在css中 `内容必须在行盒中` `行盒和块盒不能相邻`， 这时候会补充 匿名行盒 + 匿名块盒）

布局完成后，会得到一棵带有布局信息的树  布局树

布局阶段会依次遍历 DOM 树中的每个节点，为其计算出精确的位置和大小信息。

大部分情况下，布局树和dom树 不是一一对应的，

比如 匿名行盒 + 匿名块盒等
比如 display: none 的节点没有几何信息，因此也不会出现在布局树中。
伪元素选择器 虽然dom树中不存在这些节点，但他们拥有几何信息。所以会在布局树中。

第四步：`分层` layer （谷歌浏览器中 有分层调试 layers）

主线程会使用一套复杂的策略对布局树中进行分层

分层的好处在于，将来某一个层改变后，仅会对该分层进行后续的处理，从而提升效率

滚动条、堆叠上下文、transform opacity 等样式都会或多或少的影响分层结果  也可以通过 will-change 属性更大程度的影响分层 （不能滥用）

第五步： `绘制` paint

主线程会为每个分层单独生成绘制指令集，用于描述这一分层内容如何画出来

第六步： `分块` TiLing

完成绘制后，主线程将每个图层的绘制信息交给合成线程，剩余的工作由合成线程完成。

合成线程首先对每个图层进行分块、将其划分为更多的小区域

他会从`线程池`中拿取多个线程来完成分块工作。 (线程管理器来管理分配线程)

第七步： `光栅化` Raster

分块完成后，进入光栅化阶段。

合成线程会将块信息交给 GPU 进程，以极高的速度完成光栅化 (过程会用到GPU加速)

GPU 进程会开启多个线程来完成光栅化，优先处理可视区域的块

光栅化的结果，就是每个绘制块的位图（bitmap）

（gpu的计算速度很快 会高于 cpu， 什么要用gpu 不用cpu？）

第八步： `画` draw

合成线程拿到每个分层、每个块的位图后，生成一个个[指引 quad] 信息。

指引会标识出每个位图应该画到屏幕的哪个位置，以及会考虑到旋转、缩放 等变形

变形会发生在合成线程中，与渲染主线程无关， 这就是 transform 效率高的本质原因

合成线程会把 quad 提交给 GPU 进程， 由 GPU 进程产生系统调用，提交给 GPU 硬件，完成最终的屏幕成像。

`dom`
解析成dom树结构

第一步让后续的步骤不用操作字符串而是操作对象结构，当然也提供了JS操作DOM树的接口能力。

`cssom`
当HTML中嵌入css时，css的语法规则和html不一样,而他形成的结构肯定也不一样
```t
StyleSheetList  // 页面中所有样式表的集合 根节点 样式表
└── CSSStyleSheet  // 单个样式表实例
    ├── CSSStyleRule  // 样式规则1（对应 body h1 的样式）
    │   ├── 选择器：body h1
    │   └── style（样式声明）
    │       ├── color: red
    │       └── font-size: 3em
    └── CSSStyleRule  // 样式规则2（对应 div p 的样式）
        ├── 选择器：div p
        └── style（样式声明）
            ├── margin: 1em
            └── color: blue
```
样式表有哪些：
1. 外部样式表（link 标签）
2. 内部样式表（style 标签）
3. 行内样式表（style 属性）
4. 浏览器默认样式（浏览器自带的样式）（在Chrome 源码中初试化的 html.css默认样式  设置了很多默认行为， 比如div是 块盒子 display: block; ）

JS也可以操作cssom树， 比如 document.styleSheets (数组) 可以获取到所有的样式表， 也可以操作样式表中的样式规则。

让css转化成对象结构。后续的步骤不用操作字符串而是操作对象结构，当然也提供开放了JS操作cssom树的接口能力。

html 解析过程中遇到css代码
为了提高解析效率，浏览器在开始解析前，会启动一个预解析的线程，率先下载HTML中的外部 CSS 文件 和 解析css。

## 什么是 reflow（回流）

(修改的是 dom / cssom 树，重新排版  效率影响比较大)

reflow 的本质就是重新计算 layout 树

当进行了会影响布局的操作时，需要重新计算布局树，就会引发 reflow

为了避免连续的多次操作导致布局树反复计算，浏览器会合并这些操作，当 JS 代码执行完成后再进行统一计算。所以 改动属性造成的 reflow 是异步完成的

也同样因为如此，当JS 获取布局属性时（几何属性 比如 width height offsetTop offsetLeft等），就可能造成无法获取到最新的布局信息。

浏览器在反复权衡下，最终决定了获取属性 立即 reflow。

## 什么是 repaint（重绘）

repaint 的本质就是重新根据分层信息计算了绘制指令。

当改动了可见样式后，就需要重新计算，会引发 repaint。

由于元素的布局信息也属于可见样式，所以 reflow 一定会引发 repaint。

(改动了样式 就引发根据分层信息 > 到 paint 生成绘制指令集，（与几何信息无关的会跳过步骤 布局 分层） 绘制向后继续向下走)

## 为什么 transform 效率高

(因为 transform 的改变只会影响 画 draw，所以效率特别高。 transform + animation  的操作 主线程不参与从头执行。直接画 只有视口的位置变化)

因为 transform 即不会影响布局也不会影响绘制指令，他影响的只是渲染流程的最后一个 draw 阶段

由于 draw 阶段是在合成线程中，所以 transform 的变化几乎不会影响渲染主线程。 反之，渲染主线程无论如何忙绿，都不会影响 transform 的变化。

## （gpu的计算速度很快 会高于 cpu， 什么要用gpu 不用cpu？）

核心结论：GPU 适合高并行、高吞吐量的计算场景，CPU 适合复杂逻辑、低延迟的串行 / 轻并行场景，两者的硬件架构差异决定了适用场景不同，不是 “GPU 速度一定比 CPU 快”，而是在特定任务上 GPU 优势显著。
